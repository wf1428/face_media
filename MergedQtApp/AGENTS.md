# AGENTS.md — Codex 代码注释与文档维护规范

> **适用范围**：本文件所在目录及全部子目录；如子目录存在更具体的 `AGENTS.md`，在不违反本文件强制要求的前提下，可以补充该目录的约定。
>
> **执行主体**：Codex 及其他参与本仓库代码修改的自动化代理。
>
> **核心要求**：**每次新增或修改代码，都必须同步新增、核对和更新对应的文档注释。注释维护属于任务完成条件，而非可选的代码美化。**

## 1. 总则与执行优先级

1. **先理解实现，再编写注释**：注释必须反映当前代码的真实行为、边界条件和失败路径，不得凭函数名猜测、不得编造设计意图或未验证的事实。
2. **注释与代码同次交付**：新增/修改源文件、类、函数、接口、成员或协议结构时，必须在本次任务内同步维护对应注释；不得推迟到后续任务。
3. **作者署名统一为 `Du lin`**：项目自有、可编辑源文件中的文件头 `@author` 一律使用 `Du lin`。新建文件必须使用该署名；修改旧文件时，检查并统一原有项目文件头的 `@author`。**不得篡改第三方源码原始署名、许可证、版权声明、SPDX 标识或依法要求保留的归属信息。** `@author` 是项目文档署名规则，不得代替或抹去法定版权归属。
4. **日期必须真实**：使用执行修改当天的实际本地日期，格式统一为 `YYYY-MM-DD`。可在执行环境用 `date +%F` 获取；不可从示例照抄日期，不可编造创建日期或历史修改记录。
5. **旧文件必须写本次修改说明**：凡本次实际修改过的既有源文件（包括只修改注释），必须在文件级文档注释中维护 `@note`，写明**最近修改日期、修改人 `Du lin`、具体修改动作及影响**；不能只写“优化”“修改”“修复问题”等模糊描述。
6. **尊重语言语法**：C/C++ 以 Doxygen 格式为准；JavaScript/TypeScript/Vue 脚本使用 JSDoc/TSDoc；Python 使用标准 docstring；其他文件遵循其语言所允许的注释写法。JSON/JSONL 不允许直接写注释。
7. **最小必要改动**：维护注释不得擅自修改业务逻辑、接口、ABI、协议字段、默认参数、权限、线程模型或文件格式；为便于注释而需要修改实现时，必须有明确任务依据。
8. **触及即维护**：每次编辑应完成当前文件、当前变更相关符号的注释核对；无需顺带一次性重写全部历史文件。历史注释缺失按模块单独分批补齐，**纯注释补齐批次不得混入功能改动**。
9. **避免无价值注释**：注释重点回答“为什么、职责、约束、单位、所有权、异常与失败行为”，不得大量复述显而易见的语句或制造与实现冲突的说明。

## 2. Codex 每次任务的强制工作流程

### 2.1 修改前

1. 识别本次将新增或改动的文件、符号和对外行为。
2. 阅读相关声明、定义、调用路径、线程边界、配置与协议，核实注释应描述的真实行为。
3. 检查现有文件头、作者字段、类/函数/成员注释，记录缺失、过时或矛盾之处。
4. 区分**新建文件**与**既有文件**；既有文件的修改必须更新文件级 `@note`。
5. 若实际日期、返回值、错误处理或资源所有权无法确认，先查源代码和调用者；仍无法确认则如实说明待确认项，**不得编造文档内容**。

### 2.2 修改中

1. 编写或更新代码的同时，立即更新相应文档注释。
2. 如果修改函数签名、入参语义、返回值、错误码、超时、单位、并发方式、资源生命周期或协议，必须同步修改所有受影响的相关注释。
3. 对外接口优先在**头文件中的声明处**写完整 Doxygen 注释；实现文件补充算法原理、边界处理、锁保护及状态机等必要解释，避免机械复制相同注释。
4. 对仅在 `.c/.cpp` 中定义的局部函数、`static` 函数及内部类，也应在其定义前提供必要文档注释。
5. 修改旧文件时，在文件头 `@note` 中记录**本次真实修改**；若同一天多处变更，可汇总为若干具体条目。既有可信历史记录可保留，但不得伪造历史。
6. 新增配置、协议和状态变量时，补充字段含义、取值范围、默认值、位序、时间单位或状态转换约束。

### 2.3 交付前

1. 检查本次所有新建或修改文件的注释完整性、一致性与作者署名。
2. 检查 `@param` 与真实参数逐一匹配、`@return` 和失败分支一致、成员单位/所有权准确。
3. 检查旧文件 `@note` 日期为本次真实修改日期，内容准确描述修改动作和影响。
4. 确保注释没有造成语法错误，不得向 JSON、二进制、生成结果或不支持注释的文件插入非法文本。
5. 可以使用仓库现有的 Doxygen/JSDoc/lint/编译检查；未安装工具或无法执行时，在交付说明中如实报告，不得声称已经验证。
6. 最终回复简述**修改的文件、补充的注释类型、旧文件 `@note` 更新情况、检查结果和未完成项**；若某项不适用，说明原因。

## 3. C/C++：Doxygen 强制规范

### 3.1 文件头注释

所有新增项目自有 `.h/.hpp/.hh/.hxx/.c/.cc/.cpp/.cxx` 文件必须有 `/** ... */` 文件头，至少包含：

- `@file`：文件名（含扩展名），与真实文件一致。
- `@brief`：一句话概述**本文件职责**，不只是重复文件名。
- `@details`：多模块协作、主要数据流、依赖、线程模型等确有必要时填写。
- `@author Du lin`：项目统一署名。
- `@date`：**仅在能够确认新文件实际创建日期时填写**；新建文件填写执行当天日期。不得给没有可信创建信息的旧文件臆造 `@date`。
- `@note`：既有文件每次修改时必须更新，包含最近修改日期、修改人、修改动作及影响；新增文件创建时不强制写“最近修改” `@note`。

**新建文件示例：**

```cpp
/**
 * @file face_recognition.cpp
 * @brief 实现人脸特征提取、比对及识别结果转换。
 * @details 负责衔接推理输出和业务识别结果；不直接进行界面渲染。
 * @author Du lin
 * @date YYYY-MM-DD
 */
```

**修改旧文件示例：**

```cpp
/**
 * @file face_recognition.cpp
 * @brief 实现人脸特征提取、比对及识别结果转换。
 * @author Du lin
 * @note 最近修改：YYYY-MM-DD；修改人：Du lin。
 *       修改内容：
 *       1. 调整特征比对失败时的返回处理，区分无有效特征与匹配未通过。
 *       2. 更新识别接口的参数、返回值及线程调用约束说明。
 *       3. 修正阈值配置的单位和默认值文档；未改变其他识别流程。
 */
```

> 示例中的 `YYYY-MM-DD` 是占位符，**生成代码时必须替换为真实日期**。旧文件中保留确有依据的原始时间信息，不用本次修改日期冒充首次创建日期。项目文件头之外的原始版权/许可证信息应原样保留。

### 3.2 类、结构体、联合体、枚举

新增或修改的 `class`、`struct`、`union`、`enum` / `enum class` 均应具有 Doxygen 注释：

- `@brief`：职责、抽象含义及使用范围。
- `@details`：状态机、关键不变量、资源持有、生命周期、线程安全约束等复杂语义。
- `@note` / `@warning`：重要使用前提、调用顺序、不支持的场景或需要特别注意的行为。
- 枚举值使用行尾 `/**< ... */`（或同等 Doxygen 写法）说明状态含义、取值语义及影响，不仅照抄枚举名字。
- 对外共享的结构体字段说明所有权、长度、对齐、字节序、单位以及可否为空等关键约束。

```cpp
/**
 * @brief 识别模块的运行状态。
 * @details 状态只能沿初始化、待机、识别中及故障恢复路径转换。
 */
enum class RecognitionState {
    Idle,       /**< 待机：未执行识别推理。 */
    Running,    /**< 运行中：允许接收有效识别结果。 */
    Recovering, /**< 恢复中：丢弃过期结果，等待资源重新就绪。 */
};
```

### 3.3 函数、方法、构造与析构

新增函数和修改过的函数必须核对文档。按实际情况使用：

- `@brief`：明确职责及主要可观察行为。
- `@details`：复杂算法、输入限制、业务判定、回调顺序、状态转换。
- `@param[in] name`：输入参数的含义、有效范围、格式、单位、可否为空。
- `@param[out] name`：输出参数和失败时其内容是否有效。
- `@param[in,out] name`：既读又写参数；明确修改方式。
- `@return`：返回值含义、成功与失败、空指针/空容器/特殊哨兵值等；无返回值 `void` 时不写空洞的 `@return`。
- `@retval`：当明确返回多个错误码、枚举常量或状态码时，逐项列出（可与 `@return` 配合）。
- `@throws` / `@exception`：实际会抛出的异常及适用条件；不抛异常不可虚构。
- `@pre` / `@post`：调用前提、调用后的状态保证。
- `@note` / `@warning`：线程安全、阻塞/异步行为、重入、锁顺序、所有权、释放时机、时间单位、错误恢复等。
- `@deprecated` / `@see` / `@ref`：接口废弃、替代接口或相关文档，按需使用。

```cpp
/**
 * @brief 在指定等待时间内获取下一条有效识别结果。
 * @param[in] timeout_ms 最长等待时间，单位毫秒；0 表示不等待。
 * @param[out] result 成功时写入有效结果；失败时保持原值。
 * @return true 表示成功获取结果；false 表示超时、停止或内部错误。
 * @note 本方法可能阻塞调用线程，不能在需要保持流畅响应的 UI 线程调用。
 * @warning 如需区分超时和错误，应查询实际实现提供的错误状态接口。
 */
bool waitForResult(int timeout_ms, RecognitionResult& result);
```

**必须执行的细则：**

1. `@param` 名称、个数与实际函数签名**完全一致**；参数增加、删除、重命名后及时同步。默认值及其含义有业务意义时必须写清。
2. `@return` 描述必须覆盖实际所有重要返回分支；`bool`、指针、可选类型、错误码和整数哨兵值尤其需要说明。
3. 构造函数应说明资源初始化和可能失败的方式；析构函数应说明关键资源释放、线程退出或停止顺序（有特殊行为时）。
4. Qt `signals`、`slots`、异步回调、事件处理器、模板函数、重载运算符、C 风格回调和静态函数同样纳入范围；没有参数/返回值时不机械添加空标签。
5. 头文件公共 API 的注释必须让调用者**不必阅读实现**就能理解如何使用及处理失败；实现内局部细节则写在对应实现附近。
6. 维护注释时要检查函数名、参数、异常保证、`const`、`noexcept`、返回所有权与实际行为是否对应。

### 3.4 成员变量、状态标志和常量

关键成员、枚举值、配置字段与常量使用 `/**< ... */` 或同等 Doxygen 形式说明：

```cpp
int timeout_ms_ = 3000;  /**< 请求超时，单位毫秒；0 表示禁用超时（仅当实现如此定义）。 */
bool stop_requested_ = false; /**< 停止请求标志；由受保护的线程间同步机制读写。 */
uint32_t frame_id_ = 0; /**< 帧序号；说明溢出回绕规则（如实现依赖该行为）。 */
```

具体要求：

- **布尔量**：写清 `true` / `false` 的业务含义，以及何时置位、清除。
- **计数/时间**：写明 `ms`、`us`、`ns`、`s`、帧数、字节数等单位，必要时写范围及溢出行为。
- **指针/句柄**：写明拥有权、借用关系、可否为 `nullptr`、由谁释放、何时失效。
- **锁/线程/队列**：说明保护哪些成员、生产消费关系、退出与唤醒机制。
- **配置项/默认值**：说明加载来源、优先级、热更新与是否需要持久化。
- **位掩码/协议字段**：说明每一位的位置、意义、方向与字节序。
- 不要求给所有普通局部临时变量都写注释；对易误解的局部逻辑可使用简短普通注释。

### 3.5 以下关键行为必须解释清楚

涉及下列任一情形时，注释不能只写一句功能简介，应补充必要的 `@details`、`@note`、`@warning` 或就地实现说明：

| 场景 | 必须交代的关键信息 |
| --- | --- |
| 线程与互斥 | 线程归属、共享状态、锁保护对象、锁顺序、阻塞点、是否可重入、退出与 `join` 时机 |
| 异步/回调 | 回调由谁触发、在哪个线程执行、调用次数/顺序、对象生命周期、取消及超时后的处理 |
| 资源管理 | 申请和释放责任、所有权转移、异常/错误路径释放、文件描述符/内存/设备句柄有效期 |
| 配置持久化 | 读取来源、默认值、覆盖优先级、写入触发、落盘保证、重启恢复及写失败后的处理 |
| 协议与序列化 | 帧结构、长度单位、位号（bit0 是最低位还是最高位）、字节序、校验覆盖范围、转义规则 |
| 时间与计量 | 明确单位、计时基准（单调时钟/系统时间）、超时起点、边界值、溢出与回绕策略 |
| 状态机与回退 | 状态含义、进入/退出条件、超时处理、恢复/重试顺序、最大重试次数及失败兜底 |
| 硬件与驱动 | GPIO 有效电平、外设通道、DMA/缓存一致性、寄存器位意义、初始化和断电顺序 |
| 数据库与网络 | 事务边界、幂等性、失败回滚、重连、消息去重、响应码、缓冲区与数据有效期 |
| 安全与隐私 | 权限边界、敏感字段处理、日志脱敏、证书/密钥生命周期和失败关闭策略 |

**不允许假定**“线程安全”“原子写入”“必然重试”“持久化成功”等性质；只有实现确实保证时才能写入注释。

## 4. 其他文件类型

### 4.1 JavaScript / TypeScript

- 文件级注释使用 `/** ... */`、`@fileoverview`、`@author Du lin`。
- 函数/方法/导出 API 使用 JSDoc 或 TSDoc：`@param {Type}`、`@returns {Type}`、`@throws`、`@async`、`@template`、`@typedef`、`@property` 等按真实用途填写。
- TypeScript 类型由声明负责，注释重点写语义、边界和失败处理；不机械重复类型。
- 修改既有脚本必须更新文件级 `@note`，含真实日期、修改人、具体动作和影响；普通 JSDoc 工具若不识别 `@note`，需在项目文档解析配置中声明该自定义标签，或以兼容的普通描述承载同样信息。

```js
/**
 * @fileoverview 设备配置 API 的客户端封装与异常转换。
 * @author Du lin
 * @note 最近修改：YYYY-MM-DD；修改人：Du lin；修改内容：明确请求超时和非成功响应的处理路径。
 */

/**
 * @brief 获取设备的当前网络配置。
 * @returns {Promise<object|null>} 成功时返回配置对象；设备无配置时返回 null。
 * @throws {Error} 请求失败、响应无效或超时且未被内部处理时抛出。
 */
async function fetchNetworkConfig() {
    // 示例仅说明注释格式，实际实现及返回值必须与文档一致。
}
```

> 上例仅为文档写法示意，不可把示例中列出的返回行为直接套用到真实函数。

### 4.2 Vue（`.vue`）

- Vue SFC 顶部可通过 `<!-- ... -->` 描述组件职责、使用前提；在 `<script>` / `<script setup>` 内，使用 JSDoc/TSDoc 注释 `props`、`emits`、`computed`、方法、异步请求和重要状态。
- 旧组件的最近修改记录写在**组件文件头的合法 HTML 注释**中，或项目明确支持的位置；避免用不能被工具解析的 Doxygen 标记污染 Vue 模板。
- `props`、事件及回调说明必须覆盖父子组件的数据流、事件载荷、默认值和异常路径。
- 不在 `<template>`、JSON 数据段或会破坏编译/格式化的位置随意插入块注释。

```vue
<!--
@file DeviceStatus.vue
@brief 展示设备在线状态与断线重连提示。
@author Du lin
@note 最近修改：YYYY-MM-DD；修改人：Du lin；修改内容：补充离线状态提示及事件说明。
-->
<script setup>
/** @description 是否正在等待设备重新上线。 */
// const reconnecting = ref(false)
</script>
```

### 4.3 Python

- 文件开头用模块 docstring 说明用途、主要依赖及必要的使用约束；作者信息可在模块 docstring 中写 `Author: Du lin`。
- 类、函数使用 PEP 257 风格 docstring；项目若已有 Google / NumPy / reStructuredText 格式，优先沿用同一种风格。
- 函数需描述 `Args` / `Returns` / `Raises`（或对应既有格式）、关键约束及边界行为。
- 修改旧 Python 文件，在模块 docstring 中维护 `Note: 最近修改：YYYY-MM-DD；修改人：Du lin；修改内容：...`。
- 如要由 Doxygen 统一生成 Python 文档，先确认已配置兼容的输入过滤器/解析扩展，**不要假设 Doxygen 默认能完整解析所有 docstring 风格**。

### 4.4 Shell、CMake、配置及数据文件

- Shell 用 `#` 说明脚本职责、输入参数、错误退出码、副作用和清理策略；旧文件以合法 `#` 注释记录最近修改信息。
- CMake 用 `#` 说明复杂编译选项、平台条件和依赖约束；旧文件同样维护合法的最近修改说明。
- YAML / TOML / INI 等允许注释的配置文件，采用该格式合法的注释语法，重点解释可配置项、取值及单位。
- **严格 JSON / JSONL**：不得加入 `//`、`/* ... */` 或任何非法注释；相关配置说明写到邻近 README、配置说明文档、Schema 或读取它的源代码文档中。除非有明确协议约定，不添加 `_comment` 字段改变数据结构。
- 自动生成文件、第三方依赖、锁文件、二进制文件及压缩资源，原则上**不为加注释而直接编辑**；应修改生成源、配置或相应说明文档。

## 5. 旧文件最近修改记录的具体规则

1. **触发条件**：本次对既有源文件做出任何实际内容变更（新增功能、修复 Bug、重构、参数调整、仅修改注释），都必须更新该文件的最近修改说明。
2. **存放位置**：C/C++ 文件头 Doxygen 的 `@note`；JS/TS 文件级 JSDoc；Vue 合法文件头注释；Python 模块 docstring；其他语言使用其合法语法。
3. **必填字段**：最近修改日期 `YYYY-MM-DD`、修改人 `Du lin`、修改内容及影响。
4. **具体描述**：写出影响的函数/模块、调整的条件或流程、对返回值/错误处理/线程/持久化/协议/行为的影响；纯注释变更必须明确写“仅规范/补充文档注释，未调整业务逻辑”（仅当确实如此）。
5. **记录策略**：`最近修改`应反映最后一次实际改动。同一天多次更改可合并为准确、完整的记录；确需保留多个真实历史条目可另设 `@par 修改记录` 或 `CHANGELOG.md`，但不能拿历史记录代替最新 `@note`。
6. **缺少历史信息**：不得推测旧文件创建日期或过去修改人；只记录本次真实修改。发现原始作者信息、许可证或代码来源必须保留的情形，按第 1 节的第三方归属规则处理。
7. **修改日期更新范围**：只更新本次确实编辑的文件；不要批量刷新未发生改动的文件日期或虚构统一修改历史。
8. **注释质量**：禁止只写“更新注释”“优化代码”而不说明涉及对象；应使代码审查者仅看文件头即可理解本次改动范围。

## 6. Doxygen 文档质量与解析配置

- Doxygen 主要负责 C/C++；JSDoc/TSDoc、Vue 和 Python 文档可使用各自生态工具生成，并可在项目文档入口汇总，**不要求所有语言都强制通过一个 Doxygen 解析器**。
- 项目已有 `Doxyfile` 或文档配置时，应遵从其输入路径、编码、宏处理、提取策略；扩展配置时，明确使用的文件类型、过滤器、排除目录及自定义标签。
- 建议检查 Doxygen 的 `INPUT`、`FILE_PATTERNS`、`RECURSIVE`、`EXCLUDE`、`EXCLUDE_PATTERNS`、`EXTRACT_ALL`、`EXTRACT_PRIVATE`、`WARN_IF_UNDOCUMENTED`、`WARN_IF_DOC_ERROR`、`WARN_NO_PARAMDOC` 等配置与本仓库目标是否一致；不能为了消除警告盲目关闭有价值的检查。
- 重点核对参数文档警告、失效 `@ref` 链接、重复文件头、注释中的未闭合标记、代码块及 Markdown 表格。
- 若需要让 JSDoc 理解自定义 `@note` 或让其他文档工具识别 Python/Vue 元数据，应**明确添加解析/插件配置并验证输出**，不能仅凭源码有注释就宣称已生成统一文档。
- 新增 `@ingroup`、`@defgroup`、`@addtogroup`、`@see`、`@ref`、`@code` / `@endcode`、`@example` 等标记时，必须对应真实分组、引用、示例，避免无效文档链接。

## 7. 注释补齐与代码审查策略

- **常规功能任务**：只对本次受影响的文件、符号及直接相关接口补齐和更新注释，与功能变更一并交付。
- **历史补注释任务**：按模块/目录分批执行；每批**只修改注释或配套纯文档文件**，不得更改业务逻辑、格式化整个项目或混入不相关重构。
- **审查友好**：尽量保留原有代码排版和注释风格，不因补文档大范围重排无关代码。更新的文件头 `@note` 应准确对应当前 diff。
- **约束冲突处理**：若用户当次任务明确要求的修改范围与本文规则冲突，先遵守更高优先级指令；但不得静默伪造署名、日期、错误保证或破坏数据格式，并在交付说明中说明未满足项。
- **注释不是测试替代品**：注释必须与运行逻辑一致；涉及行为修改仍应执行适用的测试和构建检查。

## 8. 交付自检清单（每次必须执行）

在提交或结束本次任务前，逐项核对：

- [ ] 所有新增项目源文件都有合法文件头（`@file`、`@brief`、`@author Du lin`；实际新建日期可确认时有 `@date`）。
- [ ] 本次修改的旧文件都有真实日期、`Du lin`、具体动作及影响的最近修改 `@note`（或对应语言的合法等效说明）。
- [ ] 项目自有文件头署名统一；第三方署名、许可证、版权信息未被篡改。
- [ ] 新增/修改的类、结构体、枚举、函数和关键成员已按语言规范补全有效注释。
- [ ] `@param`、`@return`、`@retval`、`@throws` 的描述与实际签名和错误分支一致。
- [ ] 线程、回调、资源释放、配置落盘、位序/字节序、单位、状态回退等关键约束已明确说明。
- [ ] 不存在猜测性、过时、无效引用、复制粘贴错误或与实现矛盾的注释。
- [ ] 没有向 JSON 等不支持注释的文件写入非法内容；生成文件与第三方代码未被无关改动。
- [ ] 历史补齐批次未混入功能修改；普通任务未扩散到无关模块。
- [ ] 已执行可运行的语法、构建、测试、Doxygen/JSDoc 检查，或明确报告未执行原因。

**验收原则：只实现代码而遗漏本规范要求的注释，视为任务未完成。**
