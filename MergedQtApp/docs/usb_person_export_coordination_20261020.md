# 人员导出与 U 盘资源更新协调（2026-10-20）

点击“导出人员”后，在显示插盘提示之前建立独立导出预约。`udisk_watcher.sh` 确认预约后，只向导出任务提供本次 U 盘的实际挂载点，本次插入不再执行 UI、配置、视频自动复制，也不设置更新后的拔盘重启标志。

现有人员导入流程及预约协议不变，导入新增与导出一致的启动清理。人员范围、XLSX 内容、文件命名、`Ycest/person` 输出目录，以及导出后的同步和卸载流程不变。导出侧读取 `/proc/mounts` 改为 `readAll()` 后逐行解析，兼容大小报告为零的 procfs 文件；支持脚本确认的 `/media/usb0` 及其实际子挂载点。

## 预约与释放

- `/run/face-media/person-export.request`：第一行为应用 PID，第二行为本次导出令牌，由应用原子提交。
- `/run/face-media/person-export.ready`：第一行为同一令牌，第二行为脚本确认的挂载点。已经用于资源更新或人员导入的插入返回 `BUSY`，第三行携带说明。导出只接受相同令牌的确认，不自行接管正在更新的盘。
- 选择人员范围时取消、任务启动被拒绝、等待失败、任务取消、导出失败或成功，都会释放自己的预约。旧任务不能清除其他令牌的新预约；后台对象销毁时也有释放兜底。
- 本次插入一旦预约导出，完成或取消后仍需拔盘才恢复普通自动复制，避免人员导出结束后突然拷贝同一盘内的 UI。重新插入且没有有效人员预约时，恢复原有自动复制流程。

## 断电及异常退出

- 标记位于通常由内存文件系统承载的 `/run`，不保存在 U 盘或持久化业务配置中。
- 融合应用与人脸独立程序的入口均在创建 QApplication 后、建立页面和后台任务之前，分别清除遗留的导入 request、ready，以及导出 request、ready 和创建导出预约所用的锁文件。该清理只在程序启动执行，不会在正常导入或导出中途清除预约。即使旧 PID 被其他进程复用，也不会留下旧预约。
- 导入清理文件为 `/run/face-media/person-import.request` 和 `/run/face-media/person-import.ready`；导入清理函数只处理这两个文件，不触碰导出预约或业务数据。清理失败输出日志。
- 脚本检查导入和导出的预约 PID；进程已退出或请求格式无效时清除对应的失效 request、ready。PID 为 0 的导入标记也按无效请求清理，防止 `kill -0 0` 将进程组误认为预约进程。即使应用未重新启动，下一次正常插盘也不会被该失效预约占用。
- 仅重启 Qt 程序、而 U 盘监控脚本仍在运行时，脚本会保留当前插入的防重复拷贝状态直到拔盘。将盘拔出再插入，即按新一轮插入处理。
- 整机断电后重新上电，脚本是新进程，`inserted`、`job_done`、`restart_needed`、`person_session`、`export_session`、`copy_started` 及对应令牌在 `daemon_loop()` 入口全部重新初始化，不会从状态 JSON 还原旧预约或旧拷贝完成状态。首次轮询即使发现 U 盘早已挂载，也按新一轮插入处理；有效 UI 资源和读写条件满足后进入普通复制，不要求先拔盘。挂载晚于脚本启动时，后续轮询检测到挂载后同样处理。
- `face-media.service` 为 `Type=simple`，启动脚本默认延迟 5 秒启动 Qt，因此 `After=face-media.service` 不表示 Qt 已执行启动清理。整机重新上电依靠 `/run` 的重建以及脚本内存状态复位处理这段启动窗口，Qt 后续再清理导入/导出文件作为兜底；不依赖 Qt 先启动，也不增加启动等待或修改服务顺序。

断电期间正在写入的 XLSX 是否完整仍由实际写入进度和文件系统决定；清理预约只解决后续插盘被错误占用的问题。

## 部署

需要同时更新重新编译的 `MergedQtApp` 与设备 `/usr/local/sbin/udisk_watcher.sh`，然后重新启动应用及 `udisk-watcher.service`。独立运行 `FaceGateQt` 时也需重新编译对应程序。部署前拔出 U 盘，避免脚本重启时重新识别正在处理的盘。仅更新程序而保留旧脚本，导出会因收不到确认而超时，不会绕过协调直接写盘。

## 本地验证

在 Windows Qt 5.15.2 环境完成导出目标代码语法编译、后台导出对象及 moc 编译、界面头文件 moc 生成；未进行 RK3566 整体交叉编译。

隔离测试使用实际导出逻辑和后台对象，仅将控制目录、挂载表及系统命令替换为测试环境，并模拟人员表写入结果。覆盖重复预约、令牌隔离、无确认及错误确认拒绝、BUSY 拒绝、直接及子挂载点、挂载路径边界和转义、启动清理、过期预约替换、未启动对象析构释放；六条后台退出路径覆盖成功、人员表生成失败、卸载失败、同步失败、取消和 BUSY 拒绝，均检查完成信号发出前预约已释放。未验证实际 XLSX 写入或真实磁盘卸载。

实际脚本通过语法检查；其守护循环在隔离环境下运行十组场景（挂载检测、复制、重启和等待由测试替代）：导出取消、导出完成、同盘重新预约、普通复制、失效 PID、原有导入、进程失效清理、复制开始后请求导出、复制失败后请求导出、导入与导出预约同时存在。检查普通复制/拔盘重启仍执行，导出不会中途接管复制，预约插入在完成或取消后不会补做复制，拔盘后的下一次普通插入恢复复制。

补充导入启动清理验证：实际导入源代码通过语法编译；隔离测试确认即使遗留预约 PID 仍存活，启动清理也会删除导入 request、ready，孤立 ready 和重复清理均正常，不修改导出标记或业务文件；清理后新建导入预约、令牌确认和人员表临时复制仍正常。脚本新增失效导入 PID、PID 为 0、非数字 PID 三组场景，均恢复普通 UI 复制及拔盘重启；同时复查正常导入、普通复制、导入与导出预约同时存在三组场景，均通过。测试仅重定向控制目录及临时复制目录，未连接真实 U 盘。

补充“U 盘始终未拔、断电后重新上电”验证：运行实际守护循环模拟前后两次启动，保持同一挂载路径，覆盖导入处理中、导入已完成但盘仍在、导出处理中、导出已完成但盘仍在、上次普通复制已完成、上电后延迟挂载、启动清理遗留导入文件、启动清理遗留导出文件、脚本早于 Qt 启动九组场景。第二次启动刻意预置旧预约/完成状态，验证 `daemon_loop()` 初始化全部覆盖它们；每组均只进入一次普通复制流程，不要求拔插，不沿用上次的预约或拔盘重启标志。遗留文件清理场景调用实际导入及导出启动清理函数，只重定向 `/run/face-media` 路径；其他断电场景模拟 `/run` 重建，早于 Qt 启动场景额外延后调用实际清理函数。实际复制、系统重启、挂载检测和等待使用替代函数，验证范围为协调及状态流转，未模拟文件系统损坏或实际设备断电。本轮未发现该场景需要修改业务逻辑，仅补充此说明和本地隔离测试。
