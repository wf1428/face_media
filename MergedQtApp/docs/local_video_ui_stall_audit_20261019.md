# 本地视频与演示楼层同步卡顿排查

日期：2026-10-19。范围：MergedQtApp 源码、本地 Qt 5.15.2 隔离复现。未连接 RK3566 真机，本文区分已确认代码问题与现场根因推断。前文行号对应排查时源码，文末追加异步修复记录。

## 现象与判断

用户反馈本地视频播放时间较长后，约每 1～2 秒出现一次画面卡顿；声音正常，演示楼层变化也会一起卡住。

视频画布绘制、帧交付及楼层定时器都依赖 Qt 主线程，音频样本交付和输出另有 GStreamer 线程。这组现象优先指向主线程事件处理或 GUI/图形驱动提交停顿，不能仅以音频正常排除所有解码问题，也不能仅凭同时卡住认定某一个定时器已经被现场证实。

## 首要具体问题：隐藏网络页的 2 秒 DHCP 轮询同步等待外部进程

调用关系：

1. `mainwindow.cpp:215` 在主窗口构造期间创建 SettingsDialog。
2. `components/settings/settingsdialog.cpp:127` 立即创建 NetworkPage。
3. `components/settings/networkpage.cpp:382` 设置 DHCP 定时器间隔为 2000ms，构造时直接启动。没有随页面隐藏停止的逻辑。
4. `NetworkPage::syncDhcpRuntimeStateToConfig()` 在开启任一在线功能、有线 DHCP 模式且 carrier 在线时，每轮调用 `getDefaultGateway()`。
5. `networkpage.cpp:150` 的 `getDefaultGateway()` 启动 `ip route show default dev <iface>`，随后执行 `waitForFinished(2000)`。此调用在 GUI 线程同步等待；2000ms 是等待超时，并不表示每轮必然耗时两秒。
6. “参数未变化则返回”的判断位于 `networkpage.cpp:1017`，在网关查询之后，所以网络参数稳定仍会每两秒启动一次外部命令。

仓库的业务配置启用了在线功能和 DHCP，因此默认配置具备进入该路径的条件；现场配置、连接方式和真实命令耗时尚未采集。

当外部命令或系统调度变慢，主线程在这里等待期间不能正常交付视频帧或处理楼层定时事件，而音频流仍可继续。轮询周期与用户描述吻合，因此这是当前第一定位对象。Qt 官方也说明主线程调用 QProcess 的同步等待接口可能冻结界面：

https://doc.qt.io/archives/qt-5.15/qprocess.html#waitForFinished

### 本地隔离复现

从当前源码提取原 `getDefaultGateway()` 函数，保持 `QProcess::start()`、参数和 `waitForFinished(2000)` 不变，仅把工具查找结果替换为测试进程。测试进程输出合法的模拟路由，可设置自身耗时。主线程以 2000ms 定时调用该函数，同时以 10ms 心跳测量事件处理间隔。

| 对照条件 | 两次网关查询耗时 | 主线程最大事件间隔 |
| --- | --- | --- |
| 模拟路由进程不额外等待 | 80ms、32ms | 82ms |
| 模拟路由进程等待 1200ms | 1228ms、1234ms | 1235ms |

复现文件和结果位于 `.web-build/ui-stall-audit/`，包括 `ui_stall_audit.cpp`、构建文件、`fast.log`、`slow.log`。测试在 Windows Qt 上进行，证明此代码路径会把外部命令耗时直接转化为事件循环停顿；不代表已测得 RK3566 上 `ip route` 的实际耗时，也不能证明现场每次卡顿都来自它。

### 同一网络路径的其他阻塞风险

- `stopDhcpClient()` 使用最多 10 次 `QThread::msleep(100)` 等待客户端退出，合计可能约 1 秒。
- `requestAutoDhcpRenew()` 直接调用三个同步网络配置命令，每个传入 3000ms 超时。这些操作只在相应续租/重启条件下执行，不能当作每两秒必然执行的行为。
- 网络异常覆盖层 `NetworkStatusMonitor` 的检查间隔为 10 秒；默认路由回退查询有两次 800ms 同步等待。它也是 GUI 阻塞风险，但 10 秒周期与本次描述的 1～2 秒周期不直接对应。

| 路径 | 源码情况 | 本次判断 |

## 当前诊断缺口

`GstPlayerWidget::pollPlaybackDiagnostics()` 在媒体不是 `rtsp://` 时直接返回，因此当前本地视频没有相同的完整周期诊断输出。`VideoHoleWidget` 虽有 `maxPaintUs_`、`maxUploadUs_`、提交/绘制/交换间隔等字段，但当前源码没有将这些统计周期性输出。

如果仅看视频掉帧或 RGA 报错，很容易遗漏 GUI 主线程阻塞，或者把主线程恢复后出现的帧丢弃误当成原始故障。

## 确认现场根因的方法

下一轮真机采样应以同一单调时钟关联以下数据：

1. `syncDhcpRuntimeStateToConfig()` 总耗时、`getDefaultGateway()` 耗时与外部进程结果；DHCP 自动续租开始/结束时间。
2. `pollPosition()` 两个管线查询的耗时。
3. 主线程事件处理间隔及具体长事件接收者、定时器标识。
4. appsink 到达间隔、RGA 执行耗时、GUI 帧交付、纹理上传和绘制/交换间隔。

只有在画面与楼层卡住的同一时段，确认某个查询/事件耗时同步上升，或取得该时刻 GUI 线程调用栈，才能将首要定位对象升级为现场根因。如果这些主线程回调都很快而 GL 上传/交换耗时升高，应转查 GPU/Wayland 合成；如果所有 GUI 事件一起延后而没有长回调，还需看 CPU 调度、内存压力及系统 I/O。

## 建议修复边界

优先把后台 DHCP 状态采样中的外部进程查询改为异步 QProcess 或独立工作线程，GUI 只消费完成后的结果；续租重启中的同步命令和 sleep 也不能继续占用 GUI 线程。后台 DHCP 功能需要继续运行，不能简单以“网络页面隐藏”为由停掉全部轮询，否则会改变自动联网和配置同步行为。

本轮没有修改应用源码、配置、视频缩放、音频或网络行为，仅新增本排查报告和临时本地复现产物。现场根因尚待上述真机采样确认。

## 异步修复实施记录（2026-10-19）

经用户授权，在 `components/settings/networkpage.cpp` 和 `networkpage.h` 实施以下修改：

- 使用独立 `DhcpNetworkThread` 串行执行网络采样，网关查询不再占用 GUI 线程。页面隐藏时后台轮询继续工作，间隔仍为 2000ms，在线功能、有线、DHCP 和 carrier 条件沿用原逻辑。
- 自动续租中的客户端停止等待、link up、地址/路由 flush 和 DHCP 守护进程启动，以及手动/启动申请 DHCP 中原有的约 3 秒地址等待，均移至同一工作线程。
- 工作线程仅处理值对象和系统调用，界面更新、配置同步、成功信号和提示仍由 GUI 线程执行。
- 同一时刻最多存在一个网络后台任务，慢查询不会造成轮询任务堆积。更换接口、功能、连接类型或 DHCP/静态模式时，旧结果失效；续租在各系统命令之间检查失效状态，避免旧请求继续执行后续命令。
- 手动应用网络配置或离线清理若遇到运行中的 DHCP 任务，先使其失效，等当前后台调用结束后再处理，以避免静态配置被旧续租交叉覆盖。原静态网络应用命令与离线清理行为保留。
- 保留 15000ms 自动重试节流、30000ms 无有效地址时强制重试、原配置字段和成功信号语义。页面析构时等待工作线程退出，随后释放 UI，避免后台完成回调访问已释放对象。

本地验证编译了实际 NetworkPage 类、Qt Designer UI、MOC 和现有异步成员函数；测试仅替换 Linux 网卡/PID/守护进程边界，网关查询和网络命令仍实际通过 QProcess 执行可控测试进程。

模拟 1200ms 网关查询时，修复前隔离复现主线程最大事件间隔为 1235ms；修复后首次异步测试为 30ms。此对照用于验证线程隔离，不能作为 RK3566 真机性能承诺，也不能证明现场所有卡顿来源已消除。

复现与回归产物位于 `.web-build/networkpage-async-tests/`：覆盖隐藏页联网、任务合并、触发条件、断线清理、15 秒节流、30 秒强制重试、手动 DHCP、失败收束、配置变更失效及对象销毁。实际网卡、DHCP 服务和 RK3566 长时间播放仍需真机验证。
