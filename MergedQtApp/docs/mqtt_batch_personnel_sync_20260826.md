# MQTT批量人员注册处理说明（2026-08-26）

## 目标

- 服务端无需声明批次开始或结束，设备按消息逐笔处理和回复。
- IPC读取不被Base64解码、图片写盘、SQLite事务和全量图库刷新阻塞。
- 同一张在途图片的幂等重传只执行一次；处理结束后释放内存去重状态，不新增持久化幂等表。
- 只有人员、注册照文件、数据库图片路径、人脸特征和模型版本均完成提交后，才允许`Imagesresult`返回成功。

## 处理流程

1. IPC一次读取所有已到达字节，线性完成组帧，每个事件循环最多向业务层投递4帧。
2. 人员同步数据库操作进入专用线程串行执行，事务完成后立即发布对应event。
3. `face.responseImages`按请求ID和数据内容建立进程内在途键；排队或处理期间的相同消息合并，不重复解码、写盘和注册。
4. 图片响应全局逐笔处理：图片文件落盘并提交`image_path`后进行人脸质量和特征校验，再由后台线程提交最终特征事务。
5. 最终成功条件同时检查：人员存在、至少有一条人脸、所有人脸状态为`IMAGE_READY`、图片文件存在且非空、`feature_blob`非空、`model_version`非空。
6. 单张处理完成后立即发布逐图`Imagesresult`，随后释放该请求的内存去重键并处理下一张。
7. 人员列表和全量图库刷新采用2秒静默合并，连续同步最长10秒强制刷新一次；单个人员需要补图时，其`fullPersonnel`本身不触发提前刷新，由图片处理结果触发后续刷新。

## IPC保护

- mqttd发送队列条数由128扩大为512，字节上限仍为32 MiB，单帧上限仍为16 MiB。
- Qt完整帧等待区可承接mqttd队列，未完成帧缓冲上限为64 MiB。
- IPC重连后先读取mqttd状态；Broker仍连接且配置一致时跳过`apply`，避免IPC重连连带重建MQTT连接。

## 边界行为

- 设备不新增图片消息的持久化幂等记录；进程重启后由服务端未收到event的重传机制恢复。
- `sync.fullPersonnel`原有`sync_inbox`幂等逻辑保持不变。
- 图片校验失败或数据库提交失败时返回失败结果，不会把人员标记为`READY`。
- 已落盘但未完成特征事务的图片会继续被识别为未同步，下次`fullPersonnel`可重新补拉，不会因文件存在而被误判完成。
